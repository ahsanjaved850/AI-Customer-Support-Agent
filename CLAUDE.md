# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run all commands from the repo root (npm workspaces: `client`, `server`).

```bash
npm install                  # install all workspace deps

npm run dev                  # run client (5173) + server (3001) together
npm run dev:client           # client only (Vite)
npm run dev:server           # server only (tsx watch)

npm run build                # build client then server
npm start                    # run the built server (dist/index.js)

npm run create-company --workspace server -- --slug=acme --name="Acme Inc" --username=admin --password=secret
                              # provision a new company + its first admin user (see Multi-tenancy below)
```

There is no test suite and no lint script configured yet.

Per-company config (LLM provider + API key, branding — name + accent color) is set via that company's Setup page (`POST /api/c/:slug/config`), not env vars — it's persisted in `server/data/app.db` (SQLite, gitignored, plaintext API keys, local/prototype-scale only). `server/.env.example` covers `PORT`/`CLIENT_ORIGIN`/`NODE_ENV`/`TRUST_PROXY`/`CHAT_RATE_LIMIT_MAX` — see Rate limiting & error handling below. There is no `ADMIN_PASSWORD` env var — admin auth is per-company username/password, stored in the DB (see Admin auth below).

## Architecture

Monorepo with two independent TypeScript packages (both ESM — `"type": "module"` — using `NodeNext` resolution on the server) tied together by an HTTP contract under `/api`. The app is **multi-tenant**: one deployment serves any number of companies, each identified by a URL slug, with its own branding, LLM credentials, documents, and admin login. See Multi-tenancy & routing below for the full picture before touching auth, storage, or routing code.

- **client/** — Vite + React + TypeScript, styled with MUI (see Styling below), routed with `react-router-dom`. `main.tsx` wraps the tree in `<BrowserRouter>` → `<BrandingProvider>` → `<ColorModeProvider>` → `<App>`. `App.tsx` renders a shared `AppBar` (company name + dark/light toggle) around `<Routes>`: `/` (`pages/HomePage.tsx`, a placeholder), `/c/:slug` (`pages/ChatPage.tsx` — customer-facing, chat only), `/admin/:slug` (`pages/AdminPage.tsx` — company admin, wraps `SetupPanel`), and a catch-all `NotFoundPage`. `src/components/ChatWidget.tsx` owns chat state and calls `src/api.ts#sendChatStream` (see Chat streaming below). `src/components/SetupPanel.tsx` covers branding, provider/key entry, document upload + list/delete, and a manual retrieval-test box, all via `src/api.ts`. `vite.config.ts` proxies `/api` to `localhost:3001` in dev (`VITE_API_BASE` overrides for other environments).
- **server/** — Express + TypeScript (run via `tsx` in dev, compiled with `tsc` for prod). `src/index.ts` wires CORS (`credentials: true` — required for the admin session cookie)/cookie-parser/JSON parsing (256kb limit), calls `lib/db.ts#initSchema()` once at startup, and mounts all five routers under `/api/c/:slug`, each preceded by `middleware/tenant.ts#resolveTenant` (see Multi-tenancy & routing): `routes/auth.ts`, `routes/config.ts`, `routes/documents.ts`, `routes/search.ts`, `routes/chat.ts`, followed by a JSON 404 handler and a catch-all error handler (both last, in that order — see Rate limiting & error handling below).
- **RAG pipeline** (server): upload → `lib/extractText.ts` (txt/md/pdf → plain text) → `lib/chunk.ts` (paragraph-aware chunking with overlap) → `lib/embeddings.ts` → `lib/vectorStore.ts` (SQLite `documents`/`chunks` tables, both scoped by `company_id`; embeddings stored as a JSON-serialized `TEXT` column, parsed back into a `number[]` and cosine-compared in JS per search — no external vector DB or extension). `GET /api/c/:slug/search` exercises this path directly, bypassing the LLM, for testing ingestion.
- **lib/embeddings.ts** picks the embedding method from the *same* per-company config as chat: an OpenAI key uses OpenAI's embeddings endpoint; anything else (e.g. an Anthropic key, which has no embeddings API) falls back to a local on-device model (`@xenova/transformers`, lazily loaded as a singleton, shared across all companies) so setup never needs a second API key. Every exported function takes `companyId` as its first argument.
- **lib/llm.ts#chatCompleteStream** is the single provider-agnostic streaming chat function, taking `companyId` and reading `lib/config.ts` to dispatch to the OpenAI or Anthropic SDK. `lib/agent.ts#streamReply` is the one thing `routes/chat.ts` calls; it first calls `agent.ts#buildSystemPrompt` (also exported, for direct testing — both take `companyId`) which embeds the latest user message, retrieves the top 4 chunks via `vectorStore.ts#search` scoped to that company, and folds them into the system prompt — the model is instructed to use that context only when relevant and ignore it otherwise, rather than relying on a fixed similarity-score cutoff. Retrieval is best-effort: any failure (embedding error, nothing ingested) falls back to `BASE_SYSTEM_PROMPT` rather than failing the chat request.
- Both packages independently define the same `ChatMessage`/`role: 'user' | 'assistant'` shape in their own `types.ts` (no shared types package — keep them in sync manually when changing the wire format). `server/src/types.ts` also `declare global`-augments Express's `Request` with a `company: Company` field, populated by `middleware/tenant.ts` before any route handler runs.

`server/data/` (SQLite `app.db` + its `-wal`/`-shm` files) is resolved relative to the module file via `import.meta.url` in `lib/db.ts`, not `process.cwd()` — this matters because `server/dist/lib/*.js` and `server/src/lib/*.ts` both need to land on the same `server/data/` regardless of which directory `node`/`tsx` was launched from.

## Multi-tenancy & routing

One deployment, many companies, identified by a URL slug — not subdomains, not a header.

- **Data model** (`server/src/lib/db.ts#initSchema`, run once at server startup, idempotent `CREATE TABLE/INDEX IF NOT EXISTS`, no migration framework at this scale): `companies` (slug, name, accent_color, provider, api_key, model — the old single global `config.json` fields, now one row per company), `admin_users` (company_id FK, username, password_hash, `UNIQUE(company_id, username)` — usernames are unique per company, not globally), `documents` and `chunks` (both `company_id` FK; `chunks` also denormalizes `document_id`'s `filename`/`doc_type` onto every row, mirroring the old in-memory `Chunk` shape, so `search()` needs no join).
- **`server/src/lib/companies.ts`** — the only place that reads/writes `companies`/`admin_users` directly: `getCompanyBySlug`/`getCompanyById`, `createCompany`, `createAdminUser`, `verifyAdminLogin` (scrypt-hashes/verifies — see Admin auth below).
- **`server/src/middleware/tenant.ts#resolveTenant`** — mounted ahead of all five routers on every `/api/c/:slug/*` route (`index.ts`). Looks up the company by `req.params.slug`, 404s immediately if it doesn't exist, and attaches it as `req.company`. This is the single choke point that makes every route company-aware; route handlers read `req.company.id`, never a bare global.
- **Provisioning**: there's no self-serve signup — `server/src/scripts/createCompany.ts` (via `npm run create-company --workspace server -- --slug=... --name=... --username=... --password=...`) is the only way to create a company + its first admin user. Deliberate choice for prototype scale: zero public attack surface, no abuse/verification concerns to build yet. If self-serve signup is ever wanted, reuse `companies.ts#createCompany`/`createAdminUser` behind a new `POST /api/companies` route rather than duplicating the logic.
- **Client routes**: `/c/:slug` is the entire customer-facing surface — `ChatPage` renders `ChatWidget` and nothing else; there is no way to reach Setup from this tree, not even hidden in the DOM. `/admin/:slug` renders `SetupPanel`, which gates itself behind that company's admin login. `client/src/branding/BrandingProvider.tsx` is also where the current slug is derived (via `useLocation()` + a regex against `/^\/(?:c|admin)\/([^/]+)/`, not `useParams()` — this keeps it decoupled from exactly which `<Route>` renders it) and pushed into `api.ts` via `setCurrentCompanySlug()`, **synchronously during render, not inside a `useEffect`** — React completes the whole render pass before any effect runs, so this ordering guarantees the slug is set before any child component's data-fetching effect fires, even though child effects normally run before parent effects on mount.
- **`client/src/api.ts`** — every exported function (`getConfig`, `login`, `uploadDocuments`, `sendChatStream`, etc.) routes through a `companyPath()` helper that prefixes `/api/c/<currentSlug>`; there is no per-call-site slug parameter. Calling any of them with no slug set (i.e. outside `/c/:slug` or `/admin/:slug`) throws — every route in this app is company-scoped, so that's a bug, not a fallback case.
- **`client/src/lib/chatHistory.ts`** — localStorage key is now `chat-history:<slug>` (was a single `'chat-history'` key) so two companies' conversations in the same browser don't collide; `ChatWidget.tsx` reads the slug via `useParams()` (it's always rendered under `/c/:slug`, so this is fine even though `BrandingProvider` itself avoids `useParams()` — see above).

## Chat streaming

`POST /api/c/:slug/chat` streams the reply as plain text over chunked transfer — it is **not** a JSON response despite every other route being one. `routes/chat.ts` validates the request (still returning JSON on a validation error), then calls `agent.ts#streamReply(companyId, ...)`, which calls `llm.ts#chatCompleteStream(companyId, ...)` (OpenAI `stream: true` / Anthropic `messages.stream()`), writing each chunk to `res` as it arrives. Because `res.setHeader` doesn't actually send headers until the first `res.write()`/`res.end()`, an error thrown *before* any chunk is produced (e.g. no provider configured for this company) still falls through to a normal `res.status(500).json(...)` — check `res.headersSent` before assuming you can still send JSON if you touch this route.

On the client, `api.ts#sendChatStream(messages, onChunk)` reads `res.body.getReader()` and calls `onChunk` per chunk while also returning the full accumulated text once the stream ends. `ChatWidget.tsx` uses this to drive three UI states in sequence: `isWaiting` (submitted, no tokens yet → bouncing-dots `TypingDots`), `isStreaming` (first chunk arrived → live-growing `MessageBubble`), then the finished message is appended to `messages` once the stream completes. Every assistant-side bubble (indicator, in-progress, and finished) renders next to the same `AssistantAvatar` (`SupportAgentIcon`) — see `ChatWidget.style.ts`'s `MessageRow`/`AssistantAvatar`/`TypingDots`.

If you change the request/response shape here, remember `ChatResponse` was deliberately removed from `client/src/types.ts` — don't re-add a JSON response type for this route without also reverting the streaming.

## Admin auth

Gates everything that can change what a company's bot says or knows: `POST /api/c/:slug/config`, and all of `GET/POST /api/c/:slug/documents` + `DELETE /api/c/:slug/documents/:id`, and `GET /api/c/:slug/search`. **Not** gated: `GET /api/c/:slug/config` (customer-facing chat page needs it for branding) and `POST /api/c/:slug/chat` (the actual customer-facing surface).

Auth is always-on now — there is no `ADMIN_PASSWORD`/no-password no-op mode. Every company has its own admin account(s), created via the provisioning script (see Multi-tenancy & routing above).

- **`server/src/lib/companies.ts`** — `hashPassword`/`verifyPasswordHash` use `crypto.scrypt` (Node built-in, no native addon beyond `better-sqlite3`), stored as `"saltHex:hashHex"`; `verifyPasswordHash` compares via `crypto.timingSafeEqual`, same defense-in-depth as the old raw-password check it replaced. `verifyAdminLogin(companyId, username, password)` always takes a `companyId` — usernames are only unique *within* a company (`UNIQUE(company_id, username)`), so a bare username can't identify who's logging in.
- **`server/src/lib/auth.ts`** — sessions are an in-memory `Map<sessionId, {companyId, expiry}>` (24h, `SESSION_MAX_AGE_MS`) — deliberately not persisted or shared across processes; fine for a single-process, self-hosted deployment, wrong for anything multi-instance. `requireAuth` is now unconditional (no `isAuthRequired()` escape hatch) and does two checks in order: session exists and isn't expired (401 if not), **then `session.companyId === req.company.id`** (403 if not) — that second check is the security-critical line that stops a valid session cookie for Company A from authorizing requests against Company B just by changing the URL slug. `req.company` comes from `middleware/tenant.ts`, which must run before `requireAuth` on every route (it does — see index.ts's mount order).
- **`server/src/routes/auth.ts`** — `GET /auth/status`, `POST /auth/login` (body is now `{username, password}`, not just `{password}`; sets an httpOnly, `sameSite: 'lax'` cookie; `secure` only when `NODE_ENV=production`, so plain http:// dev still works), `POST /auth/logout`. `GET /auth/status` returns `authenticated: false` — not an error — both when there's no session and when the session belongs to a *different* company than the current slug, so a stale cross-tenant cookie doesn't leak "a session exists" info. `authRequired` in the response body is always `true` now (kept for client wire-format compatibility rather than removed).
- **Client**: `client/src/api.ts`'s `request()` helper always sends `credentials: 'include'` (harmless for public routes, required for gated ones) and throws `ApiError` (has `.status`) instead of a plain `Error`, so callers can distinguish a 401 (`isAuthError()`) from any other failure. `SetupPanel.tsx` checks `GET /auth/status` on mount; if not `authenticated` it renders `AdminLogin.tsx` (now with a username field, not just password) instead of its normal sections. Every mutating handler in `SetupPanel.tsx` (`handleSaveBranding`, `handleSaveKey`, `handleUpload`, `handleDelete`, `handleSearch`) routes its catch block through a local `handleAuthError(err)` helper that flips back to the login screen on a 401 (e.g. an expired session) instead of showing a generic error — follow that pattern if you add another mutating call here rather than duplicating the try/catch.
- `GET /api/c/:slug/documents` is gated even though it's a read — unlike `GET /config`, nothing customer-facing calls it (only `SetupPanel`), and it exposes internal document filenames. Same reasoning for `GET /search`: it's only used by Setup's "Test retrieval" box, and returns raw chunk text from ingested documents. `documents.ts`'s `DELETE /:id` additionally scopes its SQL `WHERE id = ? AND company_id = ?` — without that second clause, a company could delete another company's document by guessing its UUID.

## Rate limiting & error handling

- **`server/src/lib/rateLimit.ts`** exports two `express-rate-limit` instances: `chatRateLimiter` (20 req/min/IP by default, `CHAT_RATE_LIMIT_MAX` env override — applied to `POST /api/c/:slug/chat`, since that route can't be gated behind admin auth but is a direct pass-through to a paid LLM API) and `loginRateLimiter` (10 attempts/15min/IP, fixed — applied to `POST /api/c/:slug/auth/login`, to slow down password guessing). Both key on `req.ip` only (not per-company) — a deliberate simplification at this scale: one shared IP-based bucket across all companies, not `${ip}:${companyId}`, so a traffic spike on one company's chat could in principle exhaust another's shared quota. Revisit if that becomes a real problem. `req.ip` is only trustworthy if `TRUST_PROXY=1` is set *and* the server is actually behind a reverse proxy (`index.ts` only calls `app.set('trust proxy', 1)` when that env var is set — never unconditionally, since blindly trusting `X-Forwarded-For` with no proxy in front lets a client spoof their IP and dodge every limit here).
- **`index.ts`** sets an explicit `express.json({ limit: '256kb' })` rather than relying on Express's unstated 100kb default (file uploads bypass this entirely — they go through `multer`'s own 10MB-per-file limit in `routes/documents.ts`).
- **Two handlers close out `index.ts`, in this order, both after every router**: a JSON 404 (`app.use('/api', ...)`) for unmatched `/api/*` routes (this fires for a request whose method+path don't match any router's own routes; an unknown *company slug* is instead caught earlier by `resolveTenant`, which 404s before the request ever reaches a router), then a 4-arg catch-all error handler (`app.use((err, req, res, next) => ...)` — Express only treats a middleware as an error handler when it takes exactly four parameters, so don't collapse it to fewer even if some appear unused). This exists because body-parser's "payload too large" error (and any other error thrown before a route's own try/catch runs) previously fell through to Express's default handler, which returns an **HTML page containing the full stack trace and server file paths** — the catch-all logs the real error server-side via `console.error` and returns a generic JSON message to the client instead. It checks `res.headersSent` first and no-ops if so (a chat stream can be partway through `res.write()` when something goes wrong downstream).

## Branding & persistence

The app is white-labelable: each company sets its own name/accent color rather than these being fixed at build time or shared globally.

- **`server/src/lib/config.ts`**'s `AppConfig` has `provider`/`apiKey` as *optional* fields alongside `companyName`/`accentColor` — a company can set branding before ever configuring an LLM provider. `readConfig(companyId)`/`updateConfig(companyId, patch)` read/write the matching `companies` row (via `lib/db.ts`'s `db`, looked up through `lib/companies.ts#getCompanyById`) — `updateConfig` only builds `SET` clauses for fields actually present in `patch`, so saving one form (branding vs. provider/key) in Setup never clobbers the other (`routes/config.ts`'s `isCredentialUpdate` check still gates whether provider+apiKey are validated/applied at all). Note `companies.name` is `NOT NULL` in the schema — `routes/config.ts` treats an empty/whitespace `companyName` submission as "leave unchanged" rather than clearing it, since there's no more global default to fall back to per-company.
- **`client/src/branding/BrandingProvider.tsx`** fetches `GET /config` (via `api.ts`'s slug-prefixing) and exposes `{ companyName, accentColor, loading, notFound, refresh }` via `useBranding()` (throw-if-outside-provider, same pattern as `useColorMode()`). It also keeps `document.title` in sync, and now re-fetches whenever the derived slug changes (navigating between companies' pages in the same session) — see Multi-tenancy & routing above for how it derives that slug and why it must run before any child effect. Deliberately *not* cached in `localStorage` — it's server truth, fetched fast locally; caching would add a second, staleness-prone source of truth. Mounted in `main.tsx` inside `<BrowserRouter>` (needs `useLocation()`) and outside `ColorModeProvider`, since the latter reads `accentColor` from it.
- **`theme.ts`** exports `DEFAULT_ACCENT_COLOR` and both `getDesignTokens`/`getTheme` take an optional `accentColor` param — when given, `palette.primary` is just `{ main: accentColor }` and MUI's `augmentColor` derives light/dark/contrastText automatically. Reference `DEFAULT_ACCENT_COLOR` (e.g. `SetupPanel.tsx`'s color-picker default) rather than re-hardcoding the hex literal.
- **`client/src/lib/chatHistory.ts`** persists `ChatWidget`'s `messages` to `localStorage` under a per-company key (`chat-history:<slug>`, capped at 50 messages via `writeStoredMessages(slug, messages)`), following the exact try/catch-silent-failure pattern `ColorModeProvider` already established for its own localStorage use — just with `JSON.stringify`/`parse` since messages are objects. `ChatWidget.tsx` only ever writes on `[slug, messages]` changes — never on `isWaiting`/`isStreaming`/`streamingText`, which are separate state, so an in-flight reply is never persisted mid-stream. The header's reset button (`handleReset`) aborts any in-flight fetch via an `AbortController` (`sendChatStream`'s optional `signal` param) before clearing state — without the abort, a stale `onChunk` callback could still land text in the fresh conversation after reset.

## Styling

The client uses MUI (`@mui/material` — currently v9 — + MUI's own emotion-based `styled()`, not the separate `styled-components` package). No plain CSS files remain in `client/src`.

- **`src/theme/theme.ts`** is the single source of design tokens (palette, typography, shape, spacing, `components` overrides) via `getDesignTokens(mode, accentColor?)` → `getTheme(mode, accentColor?)`. Every color/radius/spacing value anywhere in the app should trace back here — don't hardcode hex codes or pixel values in a component (see Branding & persistence above for the `accentColor` override path and `DEFAULT_ACCENT_COLOR`).
- **`src/theme/ColorModeProvider.tsx`** wraps the app root (in `main.tsx`, nested inside `BrandingProvider`) with `ThemeProvider` + `CssBaseline`, persists light/dark mode to `localStorage`, reads `accentColor` from `useBranding()`, and exposes `useColorMode()`.
- **Co-located `ComponentName.style.ts`** files (e.g. `ChatWidget.style.ts`, `SetupPanel.style.ts`, `App.style.ts`) hold every non-trivial styled element for their component as named exports; the `.tsx` file imports and composes them. Trivial one-off spacing uses the `sx` prop instead of a new style-file entry. `pages/*.tsx` are thin route wrappers and don't have their own style files.
- **MUI v9 gotchas hit while building this**: `theme.shape.borderRadius` is typed `number | string`, so arithmetic on it needs `Number(theme.shape.borderRadius)` first. `styled(Box)` loses `Box`'s polymorphic `component` prop in its types — for an actual `<form>`, style `styled('form')` directly rather than `styled(Box)` + `component="form"` (see `ChatForm` / `FormBar` in the two `.style.ts` files). Icon names sometimes differ from older MUI docs (e.g. it's `@mui/icons-material/DeleteOutlined`, not `DeleteOutline`) — check `node_modules/@mui/icons-material/` if an icon import 404s at the type level.
- **`client/public/favicon.svg`** is a static copy of the `SupportAgentIcon` glyph (same one used in the AppBar and chat avatar) on `theme.ts`'s `DEFAULT_ACCENT_COLOR`. It's a static asset — it can't import `theme.ts` and doesn't follow a per-company `accentColor` override; if you ever change `DEFAULT_ACCENT_COLOR` itself, update this file's `fill` by hand to match.

## Conventions

- **Named exports only** in app code — no `export default` in `client/src` or `server/src`. The one exception is `client/vite.config.ts`, which is Vite-mandated.
- **Client path alias**: `@/*` → `client/src/*` (configured in both `vite.config.ts`'s `resolve.alias` and `tsconfig.json`'s `paths` — both are required, the tsconfig entry alone doesn't affect the Vite runtime; `tsconfig.json`'s `paths` works without `baseUrl` as long as the pattern is `./`-prefixed, e.g. `"@/*": ["./src/*"]` — don't add `baseUrl` back, it's a deprecated option and unnecessary here). Use `@/...` for any cross-directory import; same-directory sibling imports (e.g. `api.ts` importing `./types` from the same folder) stay relative.
- **No path alias on the server** — it's plain Node ESM with no bundler, and the imports are already shallow (one directory level). Don't introduce one without also solving dev (`tsx`) vs. compiled (`dist`) resolution consistently.
